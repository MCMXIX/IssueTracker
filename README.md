# Issue Tracker

A support inbox for triaging issues, adding comments, and tracking changes. A
background worker generates a short summary and a suggested next action for each
new issue. The Vue interface includes a filterable inbox, an issue form, and a
detail page with comments and recent audit history.

## Run locally

Start Docker Desktop or Docker Engine with the Compose plugin. Run these
commands from the repository root.

```sh
cp .env.example .env
docker compose build app
docker compose run --rm --no-deps app php artisan key:generate --show
```

Paste the generated value into `APP_KEY` in `.env`. Then start the services and
apply the migrations and demo seed.

```sh
docker compose up --wait
docker compose exec app php artisan migrate --seed
```

Open [Issue Tracker](http://localhost:8000) and sign in with
`demo@example.com` and `issue-tracker-demo`. The local seeder creates two demo
users and 10 issues across all three statuses, with 25 comments and 24 audit
entries. The demo summaries are generated by local rules during seeding.

- [Laravel health check](http://localhost:8000/up)
- [Horizon dashboard](http://localhost:8000/horizon)
- [phpMyAdmin](http://localhost:8081) after running
  `docker compose --profile tools up -d phpmyadmin`. Use the MySQL username and
  password from `.env`.

The Compose file mounts the source so PHP changes are visible to the app and
Vite hot-reloads Vue and CSS. The Horizon service runs
`php artisan horizon:listen --poll` to reload workers when watched files change.
Use `docker compose up --build --wait` after changing the Dockerfile. Use
`docker compose down` to stop services while retaining the MySQL and Redis
volumes.

## API usage

### Sign in with Postman

1. Set `base_url` to `http://localhost:8000`. Keep Postman's cookie jar enabled and
   use that same hostname for every request.
2. Add `Accept: application/json` and `Referer: {{base_url}}/` to the requests.
   For requests with a body, select **Body → raw → JSON**.
3. Send `GET {{base_url}}/sanctum/csrf-cookie`. Expect `204 No Content`.
   Postman stores the session and CSRF cookies.
4. Send `POST {{base_url}}/login` with the demo credentials below. Add the CSRF
   script shown below to this and the other write requests. Expect `204`.
5. Send `GET {{base_url}}/api/me`. A `200` response with your demo user confirms
   that Postman is sending the session cookie.

```json
{
  "email": "demo@example.com",
  "password": "issue-tracker-demo"
}
```

In **Scripts → Pre-request** on login and each write request, add the script
below. Reading the cookie each time picks up the new token after login.

```javascript
const token = pm.cookies.get('XSRF-TOKEN');

if (token) {
    pm.request.headers.upsert({
        key: 'X-XSRF-TOKEN',
        value: decodeURIComponent(token),
    });
}
```

### Try the issue workflow

| Method and path | What to expect |
| --- | --- |
| `POST /api/issues` | `201` with the new ticket under `data`. Save `data.id` as `issue_id` in Postman. |
| `GET /api/issues?status=open&priority=high&category=billing` | `200` with issues that match all three filters. Results are paginated at 15 per page, and pagination links preserve the filters. |
| `GET /api/issues/{{issue_id}}` | `200` with the issue, comments oldest first, and the latest 10 audit entries newest first. |
| `PATCH /api/issues/{{issue_id}}` | `200` with the updated issue. Fields you omit keep their current values. |
| `POST /api/issues/{{issue_id}}/comments` | `201` with the saved comment. The author is the signed-in user. |
| `POST /logout` | `204` and the session ends. |

**Create an issue**

```json
{
  "title": "Duplicate charge",
  "description": "Two charges posted for invoice INV-4837.",
  "category": "billing",
  "priority": "high"
}
```

**Update its status**

```json
{
  "status": "in_progress"
}
```

**Add a comment**

```json
{
  "body": "I am checking both payment records."
}
```

If you get `401`, check `GET /api/me` and sign in again if needed. For `419`,
fetch a fresh CSRF cookie and retry. A `422` response includes field errors
under `errors`. A missing issue returns `404`.

## Background summaries

On create, the API returns `summary_status: "pending"`. Laravel dispatches the
job after the write transaction commits, and Horizon saves the summary and
suggested next action. The job sets the status to `success` or records `failed`
after a terminal failure. Vue polls the detail endpoint while generation is
pending or processing.

Changes to title, description, category, or priority clear the generated fields
and queue a new revision. A job can write only to the pending revision it was
given, so an older job cannot overwrite a newer result. Redis-backed uniqueness
and overlap locks guard against duplicate jobs for the same revision.

Leave `OPENAI_API_KEY` blank for a local run using the rules generator. To
enable Path A, set the key in your local `.env` and run
`docker compose up --wait` so Compose picks up the setting. The configured
model uses the Responses API with a structured schema, and the app validates
both fields, including the 500-character summary limit. The committed prompt
is at [resources/prompts/issue-summary-template.txt](resources/prompts/issue-summary-template.txt).
The rules generator also handles provider failures and unusable responses.

Check the worker or follow its output from the running stack.

```sh
docker compose exec app php artisan horizon:status
docker compose logs -f horizon
```

## Architecture & Decisions

| Area | Decision |
| --- | --- |
| Backend | Laravel MVC with focused actions. Controllers handle HTTP, form requests validate issue writes, resources define JSON, and `CreateIssue`, `UpdateIssue`, and `AddIssueComment` handle writes. This gave the small workflow clear boundaries and kept HTTP responses out of the actions. |
| Data | MySQL 8.4 fits the relational model. An issue has many comments and audit entries, and an audit entry belongs to its actor. Issue creation and edits save their audit records in the same transaction as the issue. The list paginates without loading relationships, and detail eager-loads comments, audit entries, and their actors. |
| Frontend | Vue 3 and TypeScript with Vite and Tailwind. Blade serves the entry page, and Vue uses the same-origin JSON API through `fetch`. We kept session authentication with CSRF protection because the app serves one team from a single origin. |
| Queue | Redis and Horizon keep generation out of the request and make job activity visible locally. The job depends on `SummaryGenerator`, so provider selection and fallback stay in the service layer. |
| Local development | One Compose file runs Laravel, MySQL, Redis, Horizon, and Vite, with phpMyAdmin available as an optional service. Mounted source files let collaborators edit and test through the same stack. |

### Trade-offs

- **Laravel MVC and actions.** A fuller domain-driven structure would add layers to a small set of
  operations. Eloquent and focused actions keep the code easy to trace,
  while a service interface supports interchangeable summary providers.
- **MySQL and Redis in Compose.** MySQL supports the foreign keys and
  transactions used for issue history. It adds a database service to run
  locally, and Horizon adds Redis and a worker. Compose starts them together,
  while the automated suite uses in-memory SQLite for isolated tests.
- **Same-origin Vue and polling.** Vue can use the JSON API with Laravel's
  session cookie. It handles validation responses and CSRF headers in the
  frontend. Polling adds a detail request every 2.5 seconds while generation
  is pending, and the flow runs without a separate real-time service.
- **OpenAI and local rules.** OpenAI can produce a more specific next action,
  at the cost of a network call and possible API charges. The local rules
  provide a repeatable result without credentials or when the provider fails.
  A summary revision and Redis locks add internal state to prevent stale
  results and duplicate work for the same revision.

The server sets `needs_attention` when creating an issue and recomputes it
when priority changes. A high-priority issue gets `true`. Low and medium get
`false`. Vue displays a red flag from that value in the inbox and detail.

## Tests

```sh
docker compose exec app composer test
```

Pest runs the automated suite against in-memory SQLite. Coverage includes session
authentication, issue validation, combined filters and pagination, detail
query counts, comments, audit entries, and summary job dispatch and outcomes.
OpenAI request and fallback behavior were tested with mocked responses. The
no-key flow was also verified with a real Horizon worker.

## Git strategy

We used `develop` as the integration branch. Authentication and the backend
features were split into focused `feature/*` branches and merged through
pull requests. That kept issue creation, updates, detail, comments, listing,
and background generation reviewable as separate changes. The Vue interface
and demo seeder followed as separate commits on `develop`.

## AI usage

I used Codex during planning to break the assessment into reviewable backend
branches, compare Laravel architecture options, and sketch the inbox, create,
and detail screens. We planned the API and queued summaries first so the Vue
screens could build on endpoints that already had tests. I chose the stack,
asked to omit Inertia, and selected the dark design before the ticket screens
were built.

During development, I implemented backend slices and asked Codex to review
them. Its reviews helped identify issues with route binding, partial updates,
audit diffs, and comment timestamps. I made revisions and asked it to check
them again. I also used Codex to help implement and verify the Docker setup,
session authentication, Pest tests, background summaries, Vue screens, and
demo seed data.

I reviewed every code suggestion and implementation generated by Codex before
committing it and merging it into `develop`.
